# Lifecycle-атомарность leave и семантика тикетов (one-time-use, nick-dedup, без глобального пароля)

Аудит нашёл компаундные отказы и семантические дыры вокруг жизненного цикла peer'а и тикета. `Room.Leave` удалял peer'а из `r.peers` только после успеха `policy.OnLeave`, а `prepareAndSendRoomStatePatch` мутировал `p.state` на месте: ошибка мастер-выборов оставляла полумутированный state и peer'а в реестре навсегда (повторный `Leave` падал `ErrPeerNotFound`, idle sweep бессилен). `Admit` был идемпотентным: переиспользованный ticket выкидывал живого peer'а через `Replace`, причём каждый ticket нёс свежий peerID — один клиент заполнял reservation reserved-слотами на TTL часа. Поле `password` HTTP-запроса проверялось дважды: и как пароль комнаты, и как глобальный `ADMISSION_PASSWORD` — парольная комната работала только при совпадении двух секретов, зная глобальный пароль можно было удалять чужие комнаты.

## Decision

- **Leave удаляет из реестра всегда (D4).** Ошибка `policy.OnLeave` логируется и возвращается, но peer считается вышедшим из `r.peers`. Инвариант «вышел из реестра» важнее «политика согласилась»: вечный zombie хуже недоставленного патча.
- **Stage-commit для leave-ветки (D4).** `prepareAndSendRoomStatePatch` работает с клоном `RoomState` и коммитит в `p.state` только после успешной мастер-выборки — полумутированного state не существует. Дивергенция мап↔state (peer в state без `r.peers`) самоизлечивается `refreshPeerPings`: запись удаляется из state и уходит клиентам патчем.
- **Ticket одноразовый (D3).** Повторный `Admit` на `admitted`-слоте → `ErrReservationAlreadyAdmitted` → JoinReject `0x75`. Реконнект — новый ticket с новым peerID; старый peer выметается idle sweep'ом (`IsAlive=false`).
- **Один outstanding reserved-слот на nick в комнате (D5).** `Reserve(ctx, roomID, peerID, nickName, expiresAt)` отклоняет `ErrTicketSlotHeld`, если в комнате есть `reserved` (не `admitted`) слот с тем же `nickName`. Admitted-слот не блокирует — реконнект живого игрока проходит.
- **`ADMISSION_PASSWORD` удалён (D1).** HTTP API key уже гейтит весь control plane; отдельный глобальный пароль в `Issue` не добавлял защиты и ломал пароль комнаты (одно поле запроса проверялось как два секрета). Пароль комнаты остаётся серверным секретом в `reservation`, хранится как SHA-256, сверка — `subtle.ConstantTimeCompare`.

## Considered Options

- **Leave только при успехе политики** — отклонено: ошибка `OnLeave` оставляла peer'а в реестре навсегда (ни клиент, ни sweep, ни `DeleteRoom` его не выводили).
- **In-place мутация + откат** — отклонено в пользу clone→commit: откат сложнее и хрупче, клон дешёв при текущих размерах state.
- **Идемпотентный `Admit` + `Replace` как семантика реконнекта** — отклонено: украденный/переиспользованный ticket молча выкидывал живого peer'а; явный новый ticket для реконнекта понятнее и уже покрывается nick-dedup.
- **Дедup по peerID** — бессмысленно (peerID свежий на каждый ticket); по IP — невозможно (reservation не знает транспорта). Nick — единственное доступное доменное поле; заодно делает nick фактически уникальным в комнате.
- **`ADMISSION_PASSWORD` в отдельное поле запроса** — отклонено: новый контракт без новой защиты (API key уже обязателен).

## Consequences

- Failed `OnLeave` больше не производит вечных zombie: peer уходит из реестра, остаток в `state.Peers` вычищает следующий тик `refreshPeerPings` (клиенты видят патч-удаление).
- Клиент обязан выпускать новый ticket на каждый реконнект; старый peer на новом peerID не «выталкивается», а доходит до eviction по `IsAlive`.
- Ник с занятым reserved-слотом отклоняется `ticket_slot_held` (`0x72`) до истечения TTL — легитимный второй человек с тем же ником ждёт или выбирает другой.
- Проверка пароля комнаты происходит ровно в одном месте (`VerifyRoomPassword`) до `Reserve`; plaintext-пароль в памяти не хранится.
- Конфиг `AdmissionConfig` потерял поле `Password`; env `ADMISSION_PASSWORD` больше не читается — молчаливо заданное значение ни на что не влияет.
